# Behavior Preserving Refactoring Guide

Version: v1

Last updated: 2026-06-25

이 문서는 기존 프론트엔드 코드를 리팩토링할 때 전과 후의 동작을 동일하게 유지하기 위한 규칙을 정리한다.

목표는 코드를 더 읽기 쉽고 유지보수하기 쉽게 바꾸되, 기능 수정이나 버그 수정을 리팩토링에 섞지 않는 것이다.

## 기본 원칙

리팩토링은 동작을 바꾸지 않는 작업이다.

현재 구현에 버그가 있더라도 리팩토링 단계에서는 같은 버그가 그대로 재현되어야 한다.

버그 수정, 기획 변경, 연출 변경, 성능 개선은 리팩토링과 분리해서 별도 작업으로 진행한다.

리팩토링 중에는 코드 구조, 이름, 파일 위치, 함수 분리만 바꾼다.

## 금지 사항

리팩토링 작업에서는 아래 변경을 금지한다.

- 조건식의 결과 변경
- 이벤트 실행 순서 변경
- 사운드 재생 순서변 변경
- 애니메이션 실행 순서 경
- store/state 업데이트 순서 변경
- `await` 추가, 삭제, 위치 변경
- timer, delay, duration 값 변경
- event name 변경
- payload shape 변경
- 외부에서 import하는 함수나 상수 이름 변경
- 버그처럼 보이는 로직 수정

위 항목을 바꿔야 한다면 리팩토링이 아니라 기능 수정 또는 버그 수정으로 분리한다.

## 허용 사항

아래 변경은 동작이 같다는 검증이 가능하면 허용한다.

- 긴 함수를 작은 함수로 분리
- 복잡한 조건식을 의미 있는 boolean 함수로 분리
- 중복된 순수 계산 로직을 함수로 추출
- 파일 역할에 맞게 코드 위치 이동
- 내부 변수명 또는 내부 함수명 개선
- 타입 정의 분리
- 상수 이름 부여
- 컴포넌트에서 계산, 판단, 변환 로직을 `.ts` 파일로 이동

단, 이동하거나 분리한 코드의 실행 시점과 실행 횟수는 바뀌면 안 된다.

## 작업 단위

한 번의 리팩토링 작업에는 하나의 목적만 둔다.

예를 들어 아래 작업을 한 번에 섞지 않는다.

- 조건 함수 추출
- 파일 분리
- 이름 변경
- 중복 제거
- 컴포넌트 분리
- 테스트 추가

작업 단위가 작을수록 전후 동작이 같은지 확인하기 쉽다.

## 리팩토링 전 체크리스트

작업 전 아래 항목을 확인한다.

- 현재 동작을 설명할 수 있는 테스트가 있는가?
- 이벤트, 사운드, 애니메이션 순서를 검증할 수 있는가?
- 변경 대상 함수의 입력과 출력이 무엇인지 확인했는가?
- 변경 대상 코드가 외부에서 import되는지 확인했는가?
- 변경 대상 코드가 store, event emitter, sound, animation, timer를 사용하는지 확인했는가?
- 버그처럼 보이는 동작을 발견했을 때 수정하지 않고 기록만 할 수 있는가?

테스트나 검증 방법이 없으면 먼저 동작 고정 테스트를 추가한다.

## 동작 고정 테스트

리팩토링 전에 현재 동작을 고정하는 테스트를 우선한다.

테스트 이름은 현재 구현의 의도를 설명한다.

현재 구현이 이상해 보여도 실제 동작을 기준으로 테스트한다.

```ts
it('freeSpinRetrigger는 positions가 비어도 현재 구현상 추가 intro와 counter update를 수행한다', async () => {
	// 현재 동작을 보존하기 위한 테스트다. 버그 여부는 별도 작업에서 판단한다.
});
```

테스트가 부족한 영역은 리팩토링 범위를 줄인다.

## 이벤트 순서 보존

book event, game event, UI event handler는 실행 순서가 동작이다.

아래 항목의 순서를 임의로 바꾸지 않는다.

- event emitter 호출
- store/state 업데이트
- sound 호출
- animation 호출
- popup open/close
- win amount 업데이트
- board symbol 업데이트
- multiplier 업데이트

순서가 중요한 코드는 함수로 분리하더라도 호출 순서를 기존과 동일하게 유지한다.

```ts
async function handleWinInfo(event: WinInfoEvent) {
	showWinSymbols(event);
	updateClusterAmount(event);
	updateTumbleList(event);
	updateTumbleWinAmount(event);
}
```

위 코드를 분리할 수는 있지만, 호출 순서를 바꾸면 안 된다.

## 비동기 코드 보존

`await` 위치는 동작에 영향을 준다.

리팩토링 중에는 `await`를 추가하거나 제거하지 않는다.

`Promise.all`, 순차 `await`, fire-and-forget 호출을 서로 바꾸지 않는다.

timer, delay, animation complete callback, Spine event callback의 실행 시점도 유지한다.

비동기 흐름을 분리해야 하면 기존 `await` 경계를 그대로 보존한다.

## Side Effect 보존

side effect가 있는 함수는 호출 시점과 호출 횟수를 보존한다.

side effect에는 아래 항목이 포함된다.

- store/state 변경
- event emitter 호출
- sound 재생 또는 정지
- animation 실행 또는 정지
- DOM 접근
- localStorage/sessionStorage 접근
- API 호출
- timer 등록 또는 해제
- console 출력

계산 로직만 순수 함수로 분리하고, side effect 실행 위치는 기존 흐름에 남긴다.

## 이름 변경 기준

외부에서 import되는 이름은 리팩토링 중에 바꾸지 않는다.

내부 변수명과 내부 함수명은 의미를 명확히 하기 위해 바꿀 수 있다.

이름 변경과 로직 분리는 가능하면 같은 작업에 섞지 않는다.

외부 계약 이름이 오타이거나 어색해도 동작 보존 리팩토링에서는 유지한다.

## 파일 분리 기준

파일을 분리할 때는 실행 흐름을 바꾸지 않는다.

분리한 파일은 기존 코드와 같은 값을 import하고 같은 값을 export해야 한다.

순수 계산, 조건 판단, payload 생성은 별도 파일로 이동하기 좋다.

event handler orchestration은 순서가 중요하므로 작은 단계로 분리한다.

파일 이동 후에는 import 경로 변경 외의 로직 변경이 섞이지 않았는지 확인한다.

## 컴포넌트 분리 기준

컴포넌트를 분리할 때는 렌더 결과와 이벤트 연결을 보존한다.

분리 전후 아래 항목이 같아야 한다.

- 렌더되는 조건
- props 값
- event handler 연결
- slot 또는 children 구조
- class/style 계산 결과
- mount/unmount 시점
- animation trigger 시점

컴포넌트 분리 중 UI 동작 개선을 같이 하지 않는다.

## 버그 발견 시 처리

리팩토링 중 버그처럼 보이는 코드를 발견해도 즉시 수정하지 않는다.

대신 아래 내용을 기록한다.

- 위치
- 현재 동작
- 버그로 의심되는 이유
- 수정하면 바뀔 수 있는 동작
- 별도 수정 작업이 필요한지 여부

버그 수정은 리팩토링 완료 후 별도 작업으로 진행한다.

## 완료 조건

리팩토링 완료 전 아래 항목을 확인한다.

- 테스트가 통과한다.
- build가 통과한다.
- 변경 전후 public API가 같다.
- 이벤트 순서가 같다.
- 사운드와 애니메이션 순서가 같다.
- 기존 버그를 의도치 않게 수정하지 않았다.
- 리팩토링 목적과 관계없는 변경이 섞이지 않았다.

위 조건을 만족하지 못하면 리팩토링 범위를 줄인다.
